# 调优记录 · 轮次 32：把「原生 4-bit」的每条路都摸清楚

日期：2026-08-14
承接：轮次 31（发现我们在以模型原生 1.9 倍的权重流量运行）

轮次 31 确认原始 0731 权重是 4-bit（156 GB，专家占 90% 字节），而我方 w8a8 是 292 GB。
瓶颈就是每步搬多少字节专家权重，所以"回到原生 4-bit"是唯一还有量级空间的方向。

本轮的问题是：**能不能读 gfx936 的 4-bit 内核源码，为 gfx928 重写？**
答案是：这个前提不成立，但沿着它查下去找到了更有价值的东西。

## 一、先纠正前提：4-bit 没有 gfx936 二进制可读

轮次 28 的说法需要更精确。低比特算子（`cutlass_w4a8_moe_mm`、`gptq_gemm`、
`awq_dequantize` 等）**不是"编了 gfx936 没编 gfx928"，而是对所有架构都不存在于这个
ROCm 构建中**——`sgl_kernel` 本身含 gfx928 代码，但这些 op 在 `torch.ops` 里取不到。
所以没有可反汇编的目标。

（真正"只编了别的架构"的是 `deep_ep`，含 gfx936/gfx938。但那条也不该反汇编：
DeepEP 与 RocSHMEM 都是开源的，从源码加一个 offload-arch 重编远比分析二进制便宜。）

## 二、sglang 其实认得 DSV4 的 fp4 专家

启动日志里有一行此前没注意的：

```
Auto-detected DSV4 routed-expert layout: is_fp4_experts=True
```

`layers/quantization/fp8.py` 里有一张完整的后端映射表：

| `--moe-runner-backend` | fp4 专家走哪条 | 在 gfx928 上 |
|---|---|---|
| `auto`（当前默认） | **反量化 fp4 → fp8**，走 `Fp8MoEMethod` | ✅ 能跑，**但等于 8-bit** |
| `marlin` | `Mxfp4MarlinMoEMethod` | ❌ marlin 是 CUDA 专属 |
| **`humming`** | **`Mxfp4HummingMoEMethod`** | ⚠️ 见下 |
| `flashinfer_mxfp4` | SM90/SM100 专用分支 | ❌ CUDA 专属 |

**第一行就解释了轮次 31 的观测**：即使喂原始 fp4 权重，默认 `auto` 也会在加载时
把 fp4 反量化成 fp8。也就是说"跑在 8-bit 上"不是我方量化管线的选择造成的，
而是这条代码路径的既定行为——我们的 w8a8 只是把同一件事提前做了。

## 三、humming：集成代码发了，库没发

`humming` 和 `lightop` 一样是海光特有后端（不是上游 sglang 的名字），
`--moe-runner-backend` 的取值列表里两个都在。

sglang 侧的集成是完整的：

- `layers/quantization/mxfp4_humming_moe.py`（3178 字节，2026-08-11）
- `layers/quantization/humming_utils.py`（5177 字节，同日）

但 `humming_utils.py` 第 5 行：

```python
from humming.layer import HummingInputSchema, HummingMethod
```

而 `humming` 这个包**在镜像里不存在**（`importlib.util.find_spec('humming')` 返回 None；
对照 `lightop` 返回可用）。

**结论：gfx928 上唯一可能承载原生 mxfp4 专家的后端，其依赖库没有随镜像发布。**

这是继「DeepEP 编错架构」「低比特算子没编进来」之后的第三种缺失形态：
**集成层发了，实现层没发。**

> 附带一提，`mxfp4_humming_moe.py` 里出现了 `_mega_moe_weights_built` 标记——
> 轮次 26 结尾提过的 MegaMoE 融合调度，在这条路径里是真实存在的。

## 四、自助路线：Triton int4（可行但未验完）

不依赖厂商的另一条路是 `moe_wna16` + AWQ int4，走 Triton：

- `fused_moe.py` 里有 `use_int4_w4a16` 路径，**Triton 实现**
- Triton 是运行时 JIT，按当前架构现场生成代码——**不存在移植问题**
- `moe_wna16.py` 的 AWQ 分支写着 `if not _is_hcu:` 才做能力检查，
  即**海光专门为自家硬件放行了这条路**；本机 `is_hcu()` 返回 True
- AWQ 分支下 `use_marlin` 保持 False（GPTQ 会掉进 marlin，AWQ 不会）

实测进展：内核**确实为 gfx928 编译并执行了**（配置查找打出
`dtype=int4_w4a16`，无 VM fault，返回正常形状的张量）。

但用合成张量做数值验证**没有成功**：全零权重与随机权重都得到全零输出；
换成常数权重后触发 VM fault。张量形状已按 `moe_wna16.py` 的 `create_weights` 对齐
（包括零点也按每字节两值打包这个坑），仍未跑通。

**诚实结论：这是探针的问题，不是平台的结论。** AWQ 的 nibble 排列有特定顺序
（不是简单的高低半字节），手工构造权重等于盲写一遍打包逻辑。
**要验证这条路，必须走真实加载器 + 真实 AWQ 权重**，而那就是量化工作本身。

（过程中还有一个教训：会段错误的探针不能和服务共用 GPU——VM fault 会把同卡上
正在服务的进程一起带崩，本轮因此多重启了一次。）

## 五、给海光的诉求（本轮新增两条，优先级最高）

| # | 诉求 | 收益 |
|---|---|---|
| **1** | **随镜像发布 `humming` 包，并为 gfx928 构建** | 原生 mxfp4 专家，**零重新量化**，权重流量直接减半 |
| **2** | 低比特算子族（`cutlass_w4a8_moe_mm` 等）补进 ROCm 构建 | 另一条 4-bit 路 |
| 3 | DeepEP/RocSHMEM 补 gfx928 编译目标 | 专家并行，每步权重读取量约降到 1/5 |
| 4 | 修 EP 朴素 dispatcher 的 gfx928 非法地址访问 | 专家并行备选路 |
| 5 | 修 DSpark 拒绝重采样分支 | 解锁 `temperature>0` |
| 6 | triton 路由缺失（自研补丁已提供） | 已自行绕过 |

**第 1 条的性价比远高于其余**：集成代码已经写好并随镜像发出来了，缺的只是那个包。
对海光而言可能只是打包清单里漏了一项；对我们而言是权重流量减半。

## 六、我方可自助推进的下一步

若不等厂商，唯一自助路线是 **AWQ int4 量化 + Triton 路径**：

1. 先量化**一小部分**（几层或小代理模型）而不是整个 284B，用真实加载器验证路径
2. 通过后再全量量化，过完整验收（数学 / Think / Tool Call）
3. 为 `dtype=int4_w4a16` 重跑 MoE 调优（形状变了，轮次 26 的 int8 配置作废）

代价与风险：AWQ 的 int4 与模型原生 fp4 不是同一套方案，精度需实测；
`a16` 意味着激活是 bf16 而非当前的 int8，解码（访存瓶颈）受益、预填（算力瓶颈）可能变慢。
