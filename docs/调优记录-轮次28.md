# 调优记录 · 轮次 28：两条带宽杠杆都卡在 gfx928 构建缺口上

日期：2026-08-14
承接：轮次 26（瓶颈定位为权重访存带宽）、轮次 27（应用层参数调优穷尽）

轮次 27 结尾列出了仅剩的两条有量级空间的路：**专家并行 EP** 和 **4-bit MoE 权重**。
本轮把两条都走到底。结论是**都不通，但都不是原理问题，而是厂商镜像的构建目标缺口**——
三项发现对海光都是可以直接行动的诉求。

## 一、方法：先查构建目标，再决定要不要花时间

本轮最省时间的一招，是在启动任何实验之前先问一句：
**这个功能的内核，到底有没有为 gfx928 编译过？**

```bash
strings <lib>.so | grep -oE 'gfx[0-9]{3,4}' | sort -u
```

扫描镜像里的主要内核库，结果一目了然：

| 库 | 编进去的架构 | 本卡（gfx928）可用 |
|---|---|---|
| `sgl_kernel`（sglang 主内核库） | gfx906 gfx926 **gfx928** gfx936 gfx938 | ✅ |
| `aiter`（AMD 内核库） | **仅 gfx938** | ❌ |
| `deep_ep`（专家并行 a2a） | **仅 gfx936 gfx938** | ❌ |

这一张表直接解释了一个长期疑问：启动器里为什么要把 aiter 相关开关全部关掉
（`SGLANG_ROCM_USE_AITER_MOE=false`、`SGLANG_OPT_USE_AITER_MHC_PRE=0` 等一长串）。
**那不是调优偏好，是 aiter 整个库根本没有本卡的设备代码。**

## 二、专家并行 EP：两条路径，两种死法

sglang 的 a2a 后端可选 `{none, deepep, mooncake, nixl, mori, ascend_fuseep, flashinfer, megamoe}`。
先做模块可用性预筛（CPU 容器，零 GPU 占用）：

| 后端 | 模块 | 说明 |
|---|---|---|
| `deepep` | ✅ 可用 | 海光做了 ROCm 移植，自带 RocSHMEM |
| `mori` | ❌ 缺失 | |
| `megamoe` | ❌ 缺失 | 轮次 26 提过的"融合调度"，参数表里有，实现没装 |
| `flashinfer` | ❌ 缺失 | CUDA 专属 |

于是只剩 `deepep` 和 `none` 两条可试。

### 路径一：`--ep-size 8 --moe-a2a-backend deepep --deepep-mode low_latency`

启动到 MoE 首次 dispatch 时整组 abort（exit code −6）：

```
Error: hipGetSymbolAddress(reinterpret_cast<void**>(&print_lock_addr),
       HIP_SYMBOL(print_lock)): invalid kernel file (218)
       at RocSHMEM::/builds/dcutoolkit/deeplearing/DeepEP/third-party/rocshmem/...
```

调用栈：`token_dispatcher/deepep.py → dispatch` ← `ep_moe/layer.py → forward_deepep`
← `models/deepseek_v4.py`。

**`invalid kernel file (218)` 是 HIP 的"胖二进制里没有匹配当前架构的设备代码"。**
配合前面的架构扫描（`deep_ep_cpp...so` 只有 gfx936/gfx938），根因确凿：
RocSHMEM 的设备端没有 gfx928 目标。失败发生在第一次符号查找（`print_lock`）上，
也就是说这不是某个边角内核缺失，而是**整个 RocSHMEM 设备侧对本卡不可用**。

> 这一条对海光是**单个编译参数**的事：把 gfx928 加进 DeepEP/RocSHMEM 的
> offload-arch 列表即可。功能代码已经写好并移植完成，只差没为本卡出一份。

### 路径二：`--ep-size 8 --moe-a2a-backend none`（朴素 dispatcher）

这条走得更远——权重加载正常、显存回到 62.69 GB（说明前一条里 DeepEP 预分配了约 38 GB 缓冲）、
cuda graph 捕获列表也恢复成完整的 `[1..16]`——但在图捕获阶段段错误（exit code −11）：

```
Invalid address access: 0x7825611c0000, Error code: 1
  at sglang/srt/layers/moe/fused_moe_triton/layer.py:1350 forward_impl
```

即 EP 分片下的 fused_moe_triton 前向存在非法地址访问。这是一个独立于 DeepEP 的
**gfx928 正确性缺陷**，与轮次 24 的 DSpark 并发硬件异常属同一类（看不到栈的显存/地址问题）。

### 附带发现：DeepEP 会缩小 cuda graph 捕获范围

`deepep + low_latency` 模式下，验证图的捕获批量从 TP 基线的
`[1, 2, 3, 4, 5, 6, 7, 8, 10, 12, 14, 16]` 缩到了 **`[4, 8, 12, 16]`**——**bs=1 未被捕获**。

也就是说，即便 RocSHMEM 的架构问题解决了，EP + low_latency 也会让单流解码回退 eager。
轮次 27 里被证伪的那条 cuda graph 假设，在 EP 配置下反而成立。
**同一个参数在不同配置下的行为不能互相套用**——这已经是本项目第三次踩到这个模式
（轮次 25 的 KV dtype 是第一次，轮次 27 的图捕获是第二次）。

## 三、4-bit MoE 权重：算子根本没编进来

`--quantization` 的取值列表里有一整排低比特方法（`w4afp8`、`gptq`、`awq`、
`quark_int4fp8_moe`、`mxfp_w4a8`、`moe_wna16` 等），且 `sgl_kernel` 这个**确实
编了 gfx928** 的库里也能看到对应的 Python 包装函数：

```
cutlass_w4a8_moe_mm, get_cutlass_w4a8_moe_mm_data,
qserve_w4a8_per_chn_gemm, qserve_w4a8_per_group_gemm, gptq_gemm, awq_dequantize
```

看起来很有戏。但 **Python 包装存在 ≠ 算子被编进构建**。直接取 torch 算子命名空间才是权威判据
（`torch.ops` 用惰性 `__getattr__`，`dir()` 不枚举算子，用 `dir()` 会得到错误结论）：

| 算子 | 是否注册 |
|---|---|
| `cutlass_w4a8_moe_mm` | ❌ 缺 |
| `get_cutlass_w4a8_moe_mm_data` | ❌ 缺 |
| `qserve_w4a8_per_chn_gemm` | ❌ 缺 |
| `qserve_w4a8_per_group_gemm` | ❌ 缺 |
| `gptq_gemm` | ❌ 缺 |
| `awq_dequantize` | ❌ 缺 |
| `moe_align_block_size`（对照组，生产线在用） | ✅ 在 |

对照组存在，证明探针方法有效。结论：**整个低比特算子族没有编进这个 ROCm 构建。**
`--quantization w4afp8` 这类参数能被命令行解析器接受，但背后没有本卡可用的内核。

顺带一提，`cutlass_w4a8_moe_mm` 的 docstring 明写
"leverages NVIDIA Hopper architecture features"——它本就是上游给 Hopper 的
CUTLASS 分组 GEMM，ROCm 侧要真正可用需要重新实现，不只是重编。

**这条的价值在于：它花了约 20 分钟就否掉了一条原本要花一天以上的路。**
如果先去重跑量化管线，几个小时之后才会在加载阶段撞到同一堵墙。

## 四、本轮结论

轮次 26 判定瓶颈是"每步要把 256 个专家的权重从 HBM 读一遍"，并指出两个减少读取量的方向。
本轮证明：**这两个方向在当前厂商镜像上都不可用，且都不是因为方案本身不成立。**

| 方向 | 状态 | 卡在哪 | 对海光的诉求 |
|---|---|---|---|
| 专家并行（DeepEP） | ❌ | RocSHMEM 设备代码无 gfx928 | 加编译目标（功能代码已就绪） |
| 专家并行（朴素 dispatcher） | ❌ | fused_moe_triton 前向非法地址访问 | 修 gfx928 正确性缺陷 |
| 4-bit MoE 权重 | ❌ | 低比特算子族未编进 ROCm 构建 | 补齐算子（w4a8 需 ROCm 侧实现） |

也就是说，**33 tok/s 这个天花板目前是厂商构建决定的，不是硬件决定的**。
三项都写进了 `docs/Bug报告-DSpark与triton路由.md`，其中第一项的修复成本最低、
收益最直接（理论上每步 MoE 权重读取量降到约 1/5）。

在这三项之前，应用层已无可调项。
