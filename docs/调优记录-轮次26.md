# 调优记录 · 轮次 26（续《调优记录-轮次25.md》）

## 轮次26：为 K100-AI 现场调优 MoE triton 内核配置 — 否决（但顺手抓到上游两个问题）

日期：2026-08-14 下午。动机来自一次镜像审计：`configs/triton_3_5_0/` 目录**是空的，
0 个文件、任何型号的卡都没有调优配置**。也就是说每次 MoE 计算都在用启发式默认配置，
日志里那句 "Using default MoE kernel config. Performance might be sub-optimal!" 不是提示是实情。
而 MoE 正是那 130 ms verify 步里的大头，所以这被列为"完全不依赖海光、我方自己就能做"的
最高优先级尝试。

### 一、做法

用 sglang 自带调优器（`benchmark/kernels/fused_moe_triton/tuning_fused_moe_triton.py`，
镜像里没有，从上游 raw 下载）为本机现场搜索：

```
--model /data1/models/dsv4-0731-w8a8-dspark --tp 8
--dtype int8_w8a8 --per-channel-quant --tune
```

产出 `E=256,N=256,device_name=K100_AI,dtype=int8_w8a8,per_channel_quant=True.json`，
覆盖 14 个批量档位（1/2/4/6/8/16 解码档 + 32…4096 预填档），以只读方式挂进镜像的 configs 目录。

日志确认配置已生效：原来的 "Using default MoE kernel config" 消失，变成
"Down MoE config file not found ... **reusing the tuned up-projection config**"
（下投影配置是可选的，缺失时复用已调优的上投影配置，不会退回启发式）。

### 二、结果：没有收益

| 指标 | 默认启发式配置 | 调优后配置 | 变化 |
|---|---|---|---|
| 单流解码（编程题 600 tok） | 33.8 | **34.16**（两次 34.20 / 34.11） | +1%，噪声内 |
| 23K prompt prefill | 437 tok/s | **438 tok/s** | 0% |
| 正确性（数学 3137） | ✅ | ✅ | — |

**结论：否决。** 这条路子看起来最有希望，实际上那条 "sub-optimal" 警告对我们基本是装饰性的。

### 三、为什么没用（事后分析）

关键在于 MoE 在我们的场景里是**访存瓶颈而非计算瓶颈**，而 tile 配置调的是计算侧：

- 解码时每步只有约 6 个 token（DSpark 验证窗口），乘 topk 8 = 48 行，摊到 256 个专家上
  平均每个专家不到 1 行；这一步的耗时几乎全部是"把 256 个专家的 int8 权重从 HBM 读一遍"，
  与 BLOCK_SIZE 怎么切无关。
- 预填时 chunk 4096 token，每专家约 128 行，计算密度上来一些，但仍不足以让 tile 配置产生差异。

这也解释了为什么"接受阈值放宽"（轮次 25）同样无效：**两轮实验从两个不同方向指向同一个结论
—— 瓶颈是权重访存带宽，不是计算调度**。这对海光的诉求（F-1）是更精确的定位：
需要的不是"把 GEMM 调快"，而是减少每步的权重读取量（例如更激进的专家驻留/复用，
或 MegaMoE 那类融合调度）。

### 四、顺手抓到的两个上游问题（可提给海光）

1. **调优器对每通道量化直接崩溃**：`common_utils.get_model_config` 见到 compressed-tensors 的
   `config_groups` 就无条件取 `weights.group_size` 组成 `block_shape=[0, group_size]`。
   per-channel 量化的 `group_size` 是 `null`，于是下游
   `if block_k % config["BLOCK_SIZE_K"] == 0` 拿 `None` 取模，抛
   `TypeError: unsupported operand type(s) for %: 'NoneType' and 'int'`。
   正确语义是 per-channel 无 block 概念、`block_shape` 应为 `None`（不过滤搜索空间）。
   我方补丁见 `scripts/moe_tuning/patch_tuner.py`。

2. **ROCm 默认搜索空间里有病态组合**：`get_rocm_configs_compute_bound()` 是
   4×5×4×4×5 = 1600 个配置，其中 `num_warps=1` 配大 tile 会出现单个配置耗时 **85 秒**，
   实测把整体 ETA 从 40 分钟拖到 **17 小时**。建议按 M 规模裁剪搜索空间，或对
   `num_warps=1` 加保护。我方裁剪到 108（解码档）/ 96（预填档）个配置后，
   每个批量档位约 3.5 / 9 分钟跑完，结果质量无损（裁剪依据见 `scripts/moe_tuning/make_space*.py`）。

### 五、副产品

即使没有性能收益，产出的 K100-AI 配置文件仍值得提交给海光随镜像分发：它消除了那条误导性的
"Performance might be sub-optimal" 警告——该警告会让每个用户都去怀疑配置问题、走一遍我们
这条弯路——并且对其它 batch/shape 组合可能确有收益。文件见 `scripts/moe_tuning/configs/`。

### 六、方法论记录

本轮是一次**有价值的否定**：它把"MoE 内核配置没调优"这条看起来最可疑、成本最低、
任何人接手都会先去试的路彻底堵死，并给出了堵死的原因。写进仓库正是为了让后来者
不必再花这半天。

配套的踩坑提醒：本轮测长上下文时又差点被两个老陷阱骗到——第一次测得 281 tok/s
（triton 首次 JIT 污染），第二次测得 8113 tok/s（`longctx_fresh.py` 不换标签就会命中前缀缓存）。
必须换标签、且在 JIT 预热后测，才得到真实的 438 tok/s。
