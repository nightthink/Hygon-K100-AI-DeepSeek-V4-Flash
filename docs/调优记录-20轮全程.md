1. **权重转换成功**：修复 `convert.py` 对 FP8 checkpoint 的 wo_a/wo_b `.scale` 切分

# 第二轮调优补记（2026-08-11 晚）

## 修正与新发现

1. **修正第一轮实验 2 的解读**：线上启动脚本（262144 版）本就没有 `--enforce-eager`，
   实际配置一直是 `cudagraph_mode=FULL_DECODE_ONLY`（capture sizes 1–64）。第一轮
   "去 eager" 的 sed 未改变任何配置，59.6 vs 69.6 的差异属测量波动。128 并发吞吐的
   真实波动带为 **±9%**（同配置三次实测 104.6–122.5）。
2. **关键机理洞察**：FULL_DECODE_ONLY 下 decode 前向被整体 capture，**python 侧开销
   在 replay 时不存在**。因此 eager+同步计时得到的分解（mla_core 37% / oproj 28% /
   wqb+ins 18% / in_gemms 16%）中 python 占比只作用于 prefill 与未 capture 的 batch，
   "python 换 Triton" 类优化对 decode 收益天然有限。

## 本轮三个实验

| 实验 | 结果 | 采纳 |
|---|---|---|
| DSV4_TIME 分层计时（需 cudagraph NONE，与 capture 冲突会崩） | 拿到 eager 分解（上表） | 测量手段入库 |
| capture_sizes 扩到 96/128 | 128 并发 109.3（无增益，padding 损耗） | 否，保持 1–64 |
| **o-proj 逆 RoPE Triton 化**（`inv_rope_heads_`，bit-exact，单层 3.7×） | 单流 9.1→**9.3** tok/s，正确性 7 项全过，128 并发同波动带（单次 122.5 为历史最高） | **是，已上线** |

## 当前生产状态（最终）

- 脚本：`/data1/start_dsv4_tuned.sh`（max-num-seqs 128 + capture 1–64）
- 新增内核：`/data1/dsv4_fused_ops.py` 尾部 `_inv_rope_heads_kernel`/`inv_rope_heads_`
  （备份 `*.bak_invrope`）；`vllm_mla_sparse_patched.py` 与 `mla_sparse_patched.py`
  的 `rocm_inv_rope_einsum` 已切换（带 python 参考 fallback）
- 实测：单流 **9.3 tok/s**，128 并发 **105–122 tok/s**（均值 ~111）

## 剩余优化空间的定性判断

配置层已搜索饱和；decode 的 python 开销已被 CUDA graph 吸收。剩余瓶颈是 GPU 内核
本身（mla_core 的 lightop/gemmopt 稀疏注意力、MoE int8 Triton GEMM、hipBLAS）。
进一步显著提升需要内核级工作（海光/FlagOS 上游层面），或等海光新镜像修复 `_C`
融合算子后撤销 7.2b/7.3/7.4 补丁。

# 第三轮：面向"编程环境单流优先"的 MTP 投机解码实验（2026-08-11 深夜）

## 场景约束（用户明确）

单流速度优先（编程助手）；实际并发 8–10 路，用户 ≤20；Think（思维链）能力必须保留。

## MTP 实验数据

| 项 | 结果 |
|---|---|
| 单流（普通回答） | **12.5 tok/s**（vs 基线 9.3，+34%） |
| 单流（Think 模式） | **14.3 tok/s**（推理文本 MTP 接受率更高，收益更大） |
| Think 质量 | reasoning 字段正常、思维链完整严密、答案正确——MTP 的草稿 token 全部经主模型验证，分布无损，Think 不受影响 |
| t=0 逐字复现 | 不保证（投机批量验证的数值 tie-breaking 会翻转近平票 token；数学答案一致，代码为另一等价正确实现）——质量等价，非损坏 |
| **并发稳定性** | **8 路并发即触发 GPU VMFault 引擎崩溃**（`num_speculative_tokens` 1 和 2 都崩，多轮复现，单轮 150+ fault 记录）。此前记录的"16 路崩"只是当时测点，真实阈值 ≤8 路 |

## 结论与处置

MTP 是单流性能的最大可用杠杆（+34–54%），且对 Think 无害；但**并发 VMFault 是海光
栈级 bug（GPU pagefault，闭源内核层），补丁层不可绕行**，与 8–10 路需求不兼容。
**已回滚**至稳定配置（start_dsv4_tuned.sh）：单流 9.3 tok/s，10 路并发聚合 31.4
tok/s（每路 ~3.1 tok/s），验收 7 项全过。

MTP 配置保留在 `/tmp/start_dsv4_mtp.sh`（spec=2）：若海光修复该 bug，或某实例只服务
1–2 个重度用户，可直接启用。

## 上报海光清单（更新，按优先级）

1. **[新增·最高优先] deepseek_mtp 投机解码并发 GPU VMFault**：8 路即崩，spec=1/2 均
   复现；最小复现脚本 `/data1/mtp_vmfault_repro.sh`。修复后本机单流即获 +34–54%。
2. `_C.fused_deepseek_v4_qnorm_rope_kv_rope_quant_insert` 在 gfx928 写坏 FP8 缓存。
3. indexer bf16 内核与 V4 compressor FP8 写入矛盾。
4. `rocm_inv_rope_einsum` / `fused_wkv_wgate` 的转置布局 view 冲突。
5. 优化稀疏注意力内核被注释（prefill 走纯 PyTorch 参考实现）——27B dense 24 tok/s vs
   13B 激活 MoE 9.3 tok/s 的对比数据可作为推动修复的证据。

## 编程场景的现实预期（当前配置）

- 1 路活跃：9.3 tok/s；10 路同时活跃：每路 ~3.1 tok/s（同一算子瓶颈，配置层无解）。
- 单流想上 20+ tok/s 的两条路：海光修 MTP bug（即插即用），或修稀疏注意力内核。
