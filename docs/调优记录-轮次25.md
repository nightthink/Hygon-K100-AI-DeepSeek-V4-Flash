# 调优记录 · 轮次 25（续《调优记录-轮次24.md》）

## 轮次25：DSpark 参数再优化 — 三项全否，并抓到一个"看起来更快其实全错"的陷阱

日期：2026-08-14 上午。目标：把 DSpark 单流从 33.8 tok/s 继续推向 50 tok/s。
方法：逐项试剩余的应用层旋钮，每项独立重启验证（每次约 14 分钟）。

### 一、结果总览

| # | 旋钮 | 单流（编程题 600 tok） | accept len / rate | 判决 |
|---|---|---|---|---|
| 基线 | block=5（模型默认）、阈值 1.0/1.0、fp8 KV | **33.8** | 4.38 / 0.68 | ✅ 保持 |
| 1 | `--speculative-dspark-block-size 8` | 28.3 | 4.20 / **0.40** | ❌ 否决 |
| 2 | `--speculative-accept-threshold-single 0.9` + `--speculative-accept-threshold-acc 0.8` | 33.3 | **4.55** / 0.71 | ❌ 无收益 |
| 3 | `--kv-cache-dtype bfloat16` | "44.1"（峰值 50.7） | **6.00 / 1.00** | ❌❌ **输出全是乱码** |

### 二、块大小 8：草稿更长，命中率反而崩

DSpark 的 drafter 是按 `dspark_block_size: 5` 训练的半自回归块级模型。强行把验证窗口拉到 8+1 后：
accept len 几乎不变（4.38→4.20），但 accept rate 从 0.68 掉到 0.40 —— 多草出来的 3 个 token 基本全被拒，
白白增加每步的 verify 计算量。净结果比基线慢 16%。

**结论：块大小应当锁死在模型训练值 5，它不是可调的性能旋钮。**
（轮次 23 已测过 block=3，同样更慢；至此 3 / 5 / 8 三点确认 5 是最优。）

### 三、接受阈值放宽：证明瓶颈不在投机命中率，而在 verify 前向本身

把单步阈值降到 0.9、累积阈值降到 0.8（允许"足够接近就接受"）后，accept len 确实从 4.38 涨到 4.55，
但速度纹丝不动（33.3 vs 33.8，在噪声内）。

换算一下就清楚了：

| 配置 | accept len | 单流 tok/s | 推得的 verify 步频 |
|---|---|---|---|
| 基线 | 4.38 | 33.8 | 7.72 步/s（约 130 ms/步） |
| 阈值放宽 | 4.55 | 33.3 | 7.32 步/s |

即：**每步 verify 的耗时（约 130 ms）才是天花板**，投机命中率再高也换不来速度——
多接受的那 0.17 个 token 被略微增加的接受判定开销吃掉了。

**这条数据直接支撑对海光的诉求（F-1）**：应用层已无杠杆，要到 50 tok/s 必须把
verify 前向（NSA decode 内核 + allreduce + MoE）的单步耗时从 ~130 ms 压到 ~88 ms。

### 四、【重要】bf16 KV cache 在 gfx928 的 dsv4 triton 路径上静默产出乱码

**动机**：轮次 20（Round G）在 0728 线上测得 fp8 KV 比 bf16 慢 14%，且破坏 Think。
本轮才注意到 **0811 启动器一直在跑 fp8 KV**（`SGLANG_DSV4_INT8_KV_CACHE=true` +
`--kv-cache-dtype auto` 实际解析为 `fp8_e4m3`）。于是猜测：改回 bf16 KV 也许能把
每步 130 ms 压下来。

**表面结果非常诱人**：

- 单流从 33.8 涨到 44.1（两次复现：37.4 / 50.7，第二问稳定 50+，正好达到目标值）
- accept len 6.00、accept rate 1.00（满窗全中）
- KV 池 1,026,816 → 697,600（bf16 每 token 更占地，属预期）

**但输出是彻底的乱码**：

```
问：计算 37*89-156，只给出最终数字。
答："  enc inisidg1...\n\n ( (ife for example 0...；"

问：你好，请自我介绍。
答："emic summary data ( 2. "
```

无 reasoning、无正确内容、`finish_reason` 正常返回 —— 服务不报任何错误。

**根因**：本线路的解码内核是 `triton_fp8_attention_fwd`（轮次 21 的 triton 路由补丁接进来的那个），
它按 fp8 KV 布局读 `k_cache`。喂 bf16 KV 时它照读不误，得到的是无意义数值，于是模型输出噪声。
而 DSpark 的 verify 也用同一套坏 logits，**drafter 与 target 一起错到一块去**，
所以 accept rate 显示 1.00 —— "满分"恰恰是彻底失效的信号。

**双重教训**：

1. **fp8 KV 在 0811/DSpark 线上不是可选项而是必需项**，和 0728 线的结论正好相反（不同内核路径）。
   以后引用"fp8 KV 有害"这条结论时必须带上适用范围。
2. **速度指标涨了要先怀疑正确性**。accept rate 1.00 和"忽然达标"的 50 tok/s 都是危险信号；
   任何性能改动都必须跑一遍数学 / Think / Tool Call 三项验收再采信。
   本轮如果只看 tok/s，就会把一个输出乱码的配置当成"终于达标"推上生产。

**已列为提交海光的新 Bug（P0 正确性）**：dsv4 注意力后端在 `--kv-cache-dtype bfloat16` 下
应当拒绝启动或路由到 bf16 内核，而不是静默产出乱码。详见 `Bug报告-DSpark与triton路由.md` 问题三。

### 五、本轮结论

应用层旋钮再次穷尽，**基线配置（block=5、阈值 1.0/1.0、fp8 KV）仍是最优**：单流 33.8 tok/s。
50 tok/s 的缺口只能由海光的内核优化补齐（诉求见 Bug 报告 F-1）。
