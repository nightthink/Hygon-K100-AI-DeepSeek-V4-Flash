# 调优记录 · 轮次 33：4-bit 的最后一条路也断了，但这次拿到了内核名

日期：2026-08-15
承接：轮次 32（Triton int4 被 ROCm 闸门拦住）、AWQ 工装（打包已验证）

## 一、换了个打法

前两次尝试都卡在"分不清是谁的错"：

| 尝试 | 结果 | 问题 |
|---|---|---|
| `tests/probe_int4_triton.py` | 全零 / VM fault | 张量是手搓的，不知道是内核坏还是我打包错 |
| `tests/awq_int4_probe/`（造小模型走真实加载器） | 两堵墙 | ① sglang 在 ROCm 上硬拒 `moe_wna16`；② 连未量化的 bf16 基线自己都 VM fault |

本轮换成：**用已通过 CPU 往返校验的打包逻辑造张量 → 经 sglang 自己的
`convert_awq_tensor` 转成内部布局 → 直接调 `fused_experts_impl`**。
一次绕开小模型、ROCm 闸门、Qwen2MoE 崩溃三个障碍，只问一个问题：
**喂给内核正确的 int4 张量，它算得对不对。**

## 二、逐项排除干扰因素

| # | 可能的错因 | 如何排除 |
|---|---|---|
| 1 | 我的 AWQ 打包不对 | `pack_awq.py` 用 sglang 自己的还原逻辑做逐元素往返校验，**48/48 层完全一致** |
| 2 | 内部布局不对 | 直接调用 sglang 的 `convert_awq_tensor` 生成；产出形状与 `moe_wna16.py::create_weights` 声明逐一核对（含"零点也按每字节两值打包"，即 `(E, 2N/2, K/G)`） |
| 3 | 启动配置不当 | 缺配置时默认值会产生 320 线程（超 256 launch bounds）。显式提供 `num_warps=4` 的 K100_AI 配置，日志确认 `Using MoE kernel config from ...` |
| 4 | 模型/加载器/服务层的问题 | 完全不涉及——直接调内核函数 |

## 三、结论：内核本身有缺陷，且有名字

四项干扰因素全部排除后仍然 VM fault，运行时明确报出 faulting 内核：

```
>>>>>>>> KERNEL VMFault !!!! <<<<<<
HOSTQUEUE <0x...>: kernel name: fused_moe_kernel_gptq_awq
```

**`fused_moe_kernel_gptq_awq` 是 sglang 中处理 GPTQ / AWQ 低比特 MoE 的 Triton 内核。
它在 gfx928 上以正确形成的 int4 张量非法访问显存。**

提供合规配置后重跑，仍复现 6 次 fault——**与启动几何无关**。

## 四、至此，本卡上不存在任何可用的 4-bit MoE 路径

把三轮的结论合到一起：

| 路径 | 状态 | 出处 |
|---|---|---|
| `cutlass_w4a8_moe_mm` 等预编译低比特算子 | ❌ **未编进 ROCm 构建**（`torch.ops` 取不到） | 轮次 28 |
| 原生 mxfp4 via `humming` 后端 | ❌ **`humming` 包未随镜像发布**（集成代码在，库不在） | 轮次 32 |
| `moe_wna16` + AWQ（走 Triton，不需预编译算子） | ❌ **两重阻断**：`_verify_quantization` 在 ROCm 上硬拒；即便绕开，内核本身 VM fault | 轮次 32、本轮 |
| `auto`（默认） | ⚠️ 可跑，但**把 fp4 反量化成 fp8**，等于 8-bit | 轮次 32 |

而模型的专家权重**原生就是 4-bit**（原始 156 GB vs 我方 W8A8 292 GB，专家占 90.3% 字节），
解码瓶颈正是每步搬运的专家权重字节数（轮次 26）。
**我们被迫以模型原生设计约 1.9 倍的权重流量运行，且四条路全部被平台侧阻断。**

## 五、一个待收窄的疑点

`fused_moe_kernel_gptq_awq` 同时服务 `int4_w4a16` 与 `int8_w8a16` 两种位宽。
本轮只测了 int4。**若 int8_w8a16 能跑通而 int4 崩，就能把缺陷收窄到 int4 的反量化分支**；
若两者都崩，则是整个 wna16 内核在本卡不可用。这是个便宜且有价值的后续实验。

另外注意：本轮的 fault 与以下两处**签名一致**，可能同源：

- 轮次 28：EP 朴素 dispatcher，`fused_moe_triton/layer.py:1350 forward_impl` 非法地址访问
- AWQ 工装：**未量化的** bf16 Qwen2MoE 基线，同样在 fused_moe_triton 阶段 VM fault
  （与量化无关、与维度无关；而生产 DSV4 走 `CompressedTensorsW8A8Int8MoE` 稳定运行）

即 `fused_moe_triton` 在 gfx928 上于**多种配置组合**下存在共性缺陷，
只有生产在用的那一条（int8 w8a8 + compressed-tensors）是好的。
建议贵方按"哪些 MoE 方法组合在 gfx928 上做过验证"来系统排查，而非逐个 case 修。
