# 调优记录 · 轮次 37：精度混布——用「int4 主体 + 三层 bf16」找回接受率？（结论：找不回）

日期：2026-08-15
承接：轮次 36（全量 int4 上线，accept rate 从 0.68 崩到 ~0.3，单流没赢）
起因：**"新的 int4 成果能否与前面的 w8a8 成果结合使用？"**

本轮把这个问题落成一个可证伪的实验：**精度混布**——
让 DSpark 取材相关的最后三层（layers 40/41/42）专家保留 bf16（w8a8 级精度），
其余 40 层维持 int4，看接受率是否回升。

## 一、假设

DSpark 是 MTP 自投机：draft 头吃**最后一层的隐状态**预测下一 token，
再由目标模型（全 int4 主干）验证。轮次 36 已排除法确认接受率崩塌来自
**目标模型自身分布偏移**，而非 MTP 精度。但还有一个未验证的细分假设：

> 漂移是否**集中在靠近输出端、被 draft 头直接取用的那几层**？
> 若是，只把这几层还原 bf16 就能显著回补接受率，代价极小。

如果成立，这就是 int4 与 w8a8「结合」的最优形态：一套权重里，
对投机质量最敏感的几层用高精度，其余吃 int4 的显存红利。

## 二、实现（三处关键，其余与轮次 36 v2 逐字一致）

1. **量化正则加负向先行断言**排除 40/41/42：
   `^layers\.(?!(40|41|42)\.)\d+\.ffn\.experts\.\d+\.w[123]\.weight$`
   —— 这三层专家逐字复制为 bf16 `.weight`，其余照旧 AWQ int4。
   （已单测：layers.4./14./39./43. 仍匹配，仅 40./41./42. 落空）
2. **config 的 `modules_to_not_convert` 追加** `layers.40/41/42.ffn.experts`。
   已读 sglang `moe_wna16.get_quant_method` 源码确认：被跳过且是 `FusedMoE` 时
   返回 `UnquantizedFusedMoEMethod()`（bf16），走**已修复的 moe_align 路径**
   （轮次 35 的根修复在这里再次兑现价值——没有它，这条 bf16 回退路本身就 VM fault）。
3. **增量重建**：硬链接失败（int4b 为 root 属主），改用 root 容器实拷贝 45 个未改分片，
   只重算含 40/41/42 层的 3 个分片（各 13.2GB bf16，量化专家数 0）。全量 226.9GB。

**校验（config + index 双证）**：
- layers 40/41/42：每层 768 个 `.weight`（bf16），qweight = 0 ✓
- 其余层（抽查 5/39/43）：每层 768 个 `.qweight`（int4），weight = 0 ✓
- `max_total_num_tokens=2971136`（KV 池与纯 int4 一致，+33GB 权重只吃掉每卡约 4GB）

## 三、实测结果——假设被证伪

| 指标 | 纯 int4（轮次36） | **精度混布（本轮）** |
|---|---|---|
| accept len / rate | 2.4–2.9 / 0.25–0.37 | **1.6–2.9 / 0.12–0.38（均值 ~0.24）** |
| 单流解码 | 18–20 tok/s | **15.4 tok/s（11.7–17.8）** |
| KV 池 | 2,971,136 | 2,971,136（不变） |
| 每卡权重 | 20.8 GB | ~24.9 GB（+4） |

**接受率没有回升，单流反而更慢。** 三层 bf16 的 fused-MoE 走的是**未调优的
默认 triton 配置**（int4 的 tile 配置对 bf16 不适用），拖慢了这几层，
抵消了理论上的精度收益。混布版**在每一项上都不优于纯 int4**：
接受率持平、单流更慢、显存更占。

## 四、为什么找不回——机理讲清楚了

漂移**不是**集中在最后几层，而是**全主干累积**的：40 层 int4 各自贡献一点分布偏移，
到输出端时目标 logits 已整体偏离 MTP 头（在 bf16 目标上训练/固化）所"预期"的分布。
把最后 3/43 层还原 bf16，只提高了喂给 draft 头的隐状态保真度，
**却改变不了验证端——目标仍在 int4 主干上算 argmax**，与固化的 bf16 draft 头系统性错配。

一句话：**接受率是 draft 头与 int4 目标之间的对齐问题，不是某几层的精度问题。**
真正的解法是**让 draft 头重新适配 int4 目标**（用量化后目标的输出重训/校准 MTP 头），
而不是保留几层精度——那是海光在训练侧用数据做的事，超出推理调优窗口。

## 五、回到那个问题：int4 与 w8a8 能不能「结合」

能，但**不是在同一次前向里按层混精度**（本轮已证伪），而是这四种形态：

1. **同机不能同驻**：两套完整权重各约 21–36 GB/卡，8 卡放不下第二套。
   「结合」不可能是两模型同时在线。

2. **按负载/时段切换（当前最优，已具备）**：交互式低延迟走 w8a8（单流 33 tok/s），
   长上下文/高并发走 int4（KV 2.9×、64 并发 64/64）。同一镜像、同一套补丁，
   切换即换 `--model` 与量化参数——与轮次 34 的网关分流结论天然契合。

3. **补丁生态共享（已兑现的交叉收益）**：**moe_align 根修复本是为打通 int4 而生**，
   但它同时修好了 w8a8 的 bf16 未量化回退路径，并解锁了整个 `fused_moe_triton` 族。
   int4 的攻坚成果已经反哺了 w8a8 线——这是最实在的一种「结合」。

4. **w4a8 才是真正的「合成」（未来方向）**：int4 权重 + int8 激活，
   把 int4 的显存红利与 w8a8 的算子效率合到一条路上。本轮在 int4 服务日志里
   发现 `slimquant_w4a8_marlin` 后端已 `resolved_backend=lightop`——
   **lightop 侧可能已有 w4a8 的汇编路径**，值得下一步专门验证
   （需要 w4a8 打包格式 + 该内核在 gfx928 的正确性核验）。这是把两者
   在**单条推理路径**上合一的唯一正解，也正是海光一直想要的形态。

## 六、结论

精度混布作为「找回接受率」的手段被干净地证伪，代价小但收益为零。
这条负结果本身有价值：它把接受率问题从「层精度」彻底定位到「draft 头对齐」，
为海光指明真正的修复方向（重校准 MTP，而非保精度）。
int4 与 w8a8 的正确结合是**切换 + 补丁复用**（已具备）与 **w4a8 合成**（下一步，
lightop 已现线索）。混布检查点已留存于 `/home/cl/dsv4-int4mix`，量化脚本见
`scripts/int4/quant_int4_mix.py`。实验后已恢复 w8a8 生产。
