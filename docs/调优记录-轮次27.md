# 调优记录 · 轮次 27：cuda graph 假设被证伪，生产切换到 DSpark

日期：2026-08-14
承接：轮次 26（MoE 内核调优否决，瓶颈定位为权重访存带宽）

## 一、本轮的假设与结论

**假设**：0811 + DSpark 线的 `--cuda-graph-max-bs=16` 是从 0728 线（4 月版 + MTP）
继承过来的默认值，从未针对 DSpark 重调。DSpark 每步验证约 6 个 token，实际进内核的
批量是 `bs × 6`——并发 16 时是 96，远超 16。如果图捕获没覆盖到，验证路径会静默回退
eager，白白丢掉 cuda graph 的收益。

**结论：假设不成立。** 启动日志给出了决定性证据：

```
Capture target verify CUDA graph begin. backend=full, num_tokens_per_req=6,
bs=[1, 2, 3, 4, 5, 6, 7, 8, 10, 12, 14, 16], avail mem=7.52 GB
```

三点全部对上：

| 关注点 | 日志证据 |
|---|---|
| sglang 是否知道 DSpark 的 token 倍数 | `num_tokens_per_req=6` —— 知道，且内部已换算 |
| 验证路径是否被捕获 | `Capture target verify CUDA graph`，`backend=full` |
| 覆盖范围是否够 | `bs=[1..16]`，覆盖全部目标并发（实测用到 10） |

八个 TP rank 全部捕获成功，无一条失败或回退警告，捕获时余显存 7.5 GB（充裕）。
`--cuda-graph-max-bs` 在这版 sglang 里指的是**请求批量**，token 倍数由框架自己乘，
不需要使用者手工放大。**这条杠杆到此关闭。**

### 为什么这个否定值得记

这是轮次 26 之后的第二个否定结果，模式相同：**日志里最醒目的可疑点，未必是真问题。**
轮次 26 是"MoE 配置目录为空 + 满屏 sub-optimal 警告"，实测调优后 +1%；本轮是
"cuda-graph-max-bs 看起来明显没覆盖验证批"，实测框架早就处理好了。

两次的正确做法都是同一个：**先花十几分钟取证，再决定要不要花半天调**。
本轮从提出假设到证伪，成本是一次启动（约 14 分钟），没有写一行配置。

## 二、两个副产品（待评估，非本轮结论）

1. **预填充 cuda graph 被自动关闭**
   ```
   Disable prefill CUDA graph because cuda_graph_config resolved
   prefill.backend='disabled' (e.g. via --cuda-graph-backend-prefill=disabled
   or auto-disable rules)
   ```
   这版 sglang 有 `--cuda-graph-backend-prefill` 可显式开启。预填充是大批量、
   计算密集路径，内核启动开销占比小，预期收益有限，但"被规则自动关掉"这件事本身
   值得查一次触发条件。

2. **共享专家融合未启用**
   ```
   Config does not support fused shared expert(s). Shared experts fusion
   optimization is disabled.
   ```
   有 `--enforce-shared-experts-fusion` 可强制。字面意思是模型 config 不满足融合
   条件，强开是否安全未知——考虑到轮次 25 的 bf16 KV 教训（静默乱码 + 指标全面变好），
   任何"强制开启框架自己判定不支持的优化"都必须过完整正确性验收才能采信。

## 三、测量陷阱再次出现

首次生成 **12.26 tok/s**，第二次 **33.21 tok/s**——同一请求、同一服务、相隔十几秒。

12.26 这个数字极具迷惑性：它几乎正好等于文档里"0811 无投机"线的 12.3 tok/s，
第一反应是"DSpark 没生效"。实际是 triton JIT 污染，热身请求只发了 16 个 token，
不足以覆盖 400 token 生成路径上的全部内核。

**压测前必须热身两次**，这条已写进生产启动器的输出提示。

## 四、生产迁移

轮次 24/25 确认 0811 + DSpark 在贪心下全并发稳定后，本轮完成切换。

### 验收结果（切换前全部通过）

| 项目 | 结果 |
|---|---|
| 单流解码 | 33.21 tok/s（基线 33.8，热身后测） |
| 数学正确性 | 37×89−156 = 3137 ✅ |
| Tool Call | `finish_reason=tool_calls`，函数名与参数正确 ✅ |
| Think | ✅（见下方行为差异） |
| 8 并发贪心 | 8/8 成功，聚合 57.99 tok/s |
| 10 并发贪心 | 10/10 成功，聚合 63.81 tok/s |
| 长上下文检索 | 2630 token prompt，needle 命中 ✅ |

### 零停机切换手法

新配置以探针容器启动并完成全部验收后，直接 `docker rename` 成生产容器名，
**避免再花 14 分钟重跑 JIT 与图捕获**。验证过的进程就是生产进程，不重启。

### ⚠️ 行为差异：Think 改为按请求显式开启

0731 线上 `reasoning_content` 不再默认产出，需要请求携带：

```json
{"chat_template_kwargs": {"thinking": true}}
```

不带该参数时模型直接给答案（答案本身正确），但 `reasoning_content` 字段为空。
Tool Call 无此要求。**依赖 reasoning_content 的下游客户端需要同步改造**。

### ⚠️ 生产护栏

本线只在 `temperature=0` 下稳定。`temperature>0` 且并发 ≥8 会触发
`HSA_STATUS_ERROR_EXCEPTION 0x1016`，watchdog 超时后服务挂死，需重启约 14 分钟。
**网关层必须拦截高并发采样流量**，或路由到无投机备用线
（`start_0811_nospec.sh`，8 并发 52.2 tok/s，任意温度稳定）。

## 五、剩余杠杆（按性价比排序）

到这一步，**应用层参数调优已经穷尽**——轮次 25 否决了 DSpark 参数，轮次 26 否决了
MoE 内核配置，本轮否决了 cuda graph。剩下的都需要改变模型或并行布局本身：

| 杠杆 | 理论收益 | 风险与成本 |
|---|---|---|
| **专家并行 EP** (`--ep-size`) | TP=8 下每卡读全部 256 专家权重的 1/8（等效 32 个专家）；EP=8 下每卡只持 32 专家、每步只读被路由到的少数几个，理论上每步 MoE 权重读取量降到约 1/5 | 当前 `--moe-a2a-backend none` 且 `NCCL_P2P_DISABLE=1`，all-to-all 会走主机内存，可能吃光收益；DeepEP 内核大概率无 gfx928 实现。半天量级 |
| **4-bit MoE 权重**（`quark_int4fp8_moe` / `w4afp8` / `mxfp_w4a8`） | 瓶颈就是每步搬多少字节权重，8-bit → 4-bit 直接砍半 | 需重跑量化管线 + 精度验收；gfx928 上哪个 kernel 真能用未知（marlin 系是 CUDA 的，quark 是 AMD 系，最有希望）。一天以上 |
| 预填充 cuda graph / 共享专家融合强开 | 未知，预期小 | 见第二节，需完整正确性验收 |

前两条都直接指向轮次 26 定位的带宽瓶颈，是唯一还有量级空间的方向。
