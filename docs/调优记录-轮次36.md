## 一、做了什么

基于轮次 35 打通的路径，完成了**全量 284B DSV4 的 AWQ int4 量化与部署**：

1. **v1 量化**（min-max RTN）：43 层 + 3 个 MTP 模块共 35,328 个专家矩阵，
   31.7 分钟，292GB → **169.7GB**
2. **v1 服务**：加载成功（`quant=awq, bits=4`，每卡权重 20.83GB），
   输出正确（数学 3137 ✓、LRU 代码连贯）
3. **v1 问题定位**：单流 20.5 tok/s，低于 w8a8 的 33.2。DSpark accept rate
   从 0.68 崩到 0.25–0.36 —— 无校准 4-bit 量化使目标模型分布偏移，drafter 跟不上
4. **v2 量化**（α-clip：每组在 α∈{1.0..0.8} 中搜 MSE 最优截断）+ MTP 专家回退 bf16：
   198.3GB，34.8 分钟
5. **v2 服务**：accept rate 仍 0.28–0.37 —— **α-clip 无法挽回接受率**，
   分布偏移是无校准 4-bit 的固有代价

## 三、为什么单流没有赢——两个原因都查清了

1. **接受率崩塌**（主因）：DSpark 每步只兑现 2.4–2.9 个 token（原 4.38）。
   排除法确认与 MTP 精度无关（int4/bf16 MTP 两版接受率相同）——
   是**目标模型自身**分布偏移。根治需要激活感知的校准量化（AutoAWQ 全流程），
   或让 drafter 适配量化后的目标，超出本窗口。
2. **内核效率**（次因）：按步频折算约 130ms/步，与 w8a8 持平——
   权重字节减半没有转化为步速。`fused_moe_kernel_gptq_awq`（Triton，带在核解包）
   相比 lightop 的手工汇编 groupgemm 有结构性差距，调 tile 配置改善有限。

也就是说，**即便接受率完全恢复，单流也只是追平 33**。
int4 的真实红利在显存，而显存红利已全部兑现（KV 2.9×）。
