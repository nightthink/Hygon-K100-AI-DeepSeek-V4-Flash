# 调优记录 · 轮次 35：一个 bug 统一了三个"独立"故障，int4 路径全线打通

日期：2026-08-15（8 小时自由实验窗口）
承接：轮次 33（认定"内核有缺陷"并把 4-bit 判了死刑）——**本轮推翻了那个结论**

## 一、方法转变：把厂商内核当作可修的代码

此前所有轮次把 GPU 内核当厂商领地，遇到 fault 就归档报障。本轮的起点是一个
简单的觉悟：**`fused_moe_kernel_gptq_awq` 是 Triton 内核，Python 源码就在镜像里**
——和我们改过的其它 sglang 文件没有区别。而且有完美对照组：同文件里的
`fused_moe_kernel`（int8 版）在生产稳定服役。

GitHub 核对：镜像内的内核与 HYGON-AI/sglang-das 最新分支**逐字节一致**（md5 相同），
上游没有修复可捡——只能自己动手。

## 二、经验二分：内核无罪

把内核抄成带 `VARIANT` 开关的独立文件，配**手工 torch 排序**直接调用：

| 变体 | 结果 |
|---|---|
| v0 逐字原样拷贝 | ✅ **数值正确**（相对误差 0.00299） |
| v5 int8_w8a16 路径 | ✅ 数值正确（0.00297） |

**轮次 33"内核本身有缺陷"的结论错了。** 内核完全正常——问题在调用链的其它环节。

## 三、爬梯定位：真凶是 moe_align_block_size

逐级替换二分设置与真实调用链的差异：

```
L1  手工 torch 排序 + 直调内核         ✅（二分 v0）
L2  真实 moe_align + 直调内核          ❌ ← 断在这里
```

L2 的现场证据：

```
num_post = -1093386606                     ← 负数垃圾
expert_ids ∈ [-1080115515, 1062124811]     ← 未初始化内存
```

**默认的 sgl_kernel C++ 版 `moe_align_block_size` 在 gfx928 上输出纯垃圾。**
这正是刷了几十轮日志的
`Launch params (1024,1,1) are larger than launch bounds (256)` 警告——
轮次 24 曾把它标注为"无害干扰项"，**在本卡上它是真实的未定义行为**。

换 lightop 版算子（生产 w8a8 同源）后用 -777 哨兵值检查缓冲区：

```
sorted[:64] = [0, 8, 7, 15, -777, -777, ..., 1, 9, 2, 10, -777, ...]
```

**排序完全正确，但 pad 槽位不填充**——残留负垃圾骗过内核的
`token_mask`（负数 < num_valid_tokens），内核按负偏移读 A → VM fault。

## 四、修复：两行

```python
sorted_ids.fill_(topk_ids.numel())          # 预填充 pad 值
lightop.op.moe_align_block_size(...)        # 换用排序正确的实现
```

`patches/sglang-0811/patch_moe_align.py`。验证链：

| 验证 | 结果 |
|---|---|
| L6 lightop+预填充 + 直调内核 | ✅ 0.00299（与黄金结果一致） |
| L4 完整 fused_experts_impl（轮次33崩溃现场） | ✅ 正常完成 |
| tiny-MoE **bf16 基线**（AWQ 工装里崩溃的那个） | ✅ 复活 |
| tiny-MoE **AWQ int4 端到端** | ✅ 贪心前几 token 与 bf16 逐一相同后因量化噪声分叉 |

**一个 bug 统一解释并修复了三个此前认为独立的故障**：
轮次 28 的 EP 朴素 dispatcher 段错误、AWQ 工装的 bf16 基线崩溃、轮次 33 的 int4 fault
——全部走 fused_moe_triton + 坏 align；生产 w8a8 从不崩，
是因为 lightop groupgemm 路径根本不经过它。

## 六、正在进行：全量 DSV4 int4

bf16 源侦察（`dsv4-0731-bf16`，608GB）：

- 专家占 **592.7GB（97%）**；43 层 × 256 专家 + **3 个 MTP/DSpark 模块各带 256 专家**
- 命名 `layers.X.ffn.experts.N.w1/w2/w3`；w1/w3 (2048,4096)、w2 (4096,2048)，hidden=4096
- sglang 专家映射按前缀替换，`.qweight/.qzeros/.scales` 后缀自动跟随 → 与 moe_wna16 加载器兼容（tiny 模型已验证）

量化方案：RTN 非对称 int4、group=128、AWQ 打包（与已验证的 `pack_awq.py` 同一套逻辑），
主专家与 MTP 专家统一处理，非专家张量（15.7GB）原样保留 bf16。
预计产出 **~168GB**（现役 w8a8 为 292GB，**权重流量 -42%**）。

流式量化脚本 `tests/awq_int4_probe/quant_int4_dsv4.py`，GPU 加速、断点续跑，实测 ETA ~25 分钟。

## 七、方法论

1. **"厂商领地"是自我设限**——Triton 内核就是镜像里的 Python 文件，和我们打过的十几个补丁没有区别。
2. **对照组是最强的调试工具**——"同族 int8 内核在生产稳定服役"这一事实，从一开始就指向"内核外"。
3. **被标注为无害的警告要定期重审**——launch bounds 警告刷了几十轮，直到有了独立复现手段才发现它是根因。
4. **哨兵值（-777 预填充）一次暴露了"排序正确但不填充 pad"**——比读一万行内核代码快得多。
