# 调优记录 · 轮次 34：量到了一个比 tok/s 重要得多的指标——队头阻塞 86 倍

日期：2026-08-15
承接：轮次 33（4-bit 四条路全断，应用层内核方向确认穷尽）

## 一、为什么转向调度层

轮次 25–33 把内核与量化方向走到底，结论是**天花板由厂商构建与打包决定**。
调度层是唯一系统性没碰过的一层——它不改变单流 tok/s，
但决定**多请求同时到达时用户实际等多久**。

## 二、测法

编程助手场景的真实痛点不是单流速度，而是：
**某个请求正在预填长上下文时，其它交互式请求要等多久才吐出第一个字。**

`tests/bench_hol.py`：先发一个约 8K token 的长 prompt 占住预填，
1.5 秒后并发发 4 个短请求，用流式接口量 TTFT。
以"无干扰时的短请求 TTFT"为基准，算队头阻塞放大倍数。

## 三、结果：86 倍

| 场景 | 短请求 TTFT |
|---|---|
| 无干扰 | **0.64 s** |
| 长 prompt 预填进行中 | **54.79 s** |
| **放大倍数** | **86.2×** |

长请求自身 TTFT 为 56.29s——**短请求几乎等满了整个长预填**。

这个数字此前从未被测量过。作为对照：单流解码从 33 提到 50 tok/s（且已被证明
卡在权重访存带宽上，需厂商修复），对用户体感的改善远不如把这 55 秒压下来。

## 四、`--enable-mixed-chunk` 无效，但排除了一个错误假设

该开关的说明是 "mixing prefill and decode in a batch when using chunked prefill"，
看起来正对这个问题，且我方启动器一直没开。实测：

| 配置 | 受扰 TTFT 中位 | 放大倍数 | 单流解码 |
|---|---|---|---|
| A 基线（未开） | 54.79 s | 86.2× | 33.2 tok/s |
| B `--enable-mixed-chunk` | 55.66 s | **87.6×** | 33.5 tok/s |

**没有改善。** 但这个否定结果澄清了阻塞的机制：

> 阻塞不在"预填与解码混批"，而在**新请求自己的预填排在长预填后面**。
> 短请求要产出第一个 token，得先完成它自己那一小段预填；
> 而调度器在长预填占据预填批次时无法插入新的预填。

`--enable-mixed-chunk` 解决的是"解码请求被预填挤掉"，
我们遇到的是"预填请求被预填挤掉"——两回事。

顺带确认：该开关对解码性能中性（33.5 vs 33.2），误开不会有性能损失。

## 五、机制推得的下一个杠杆：把 `chunked-prefill-size` 切小

当前 `chunked-prefill-size=4096`，8K prompt 分 2 块，实测每块约 28 秒。
短请求在 t=1.5s 到达，最少要等到下一个块边界（t≈28s），
实测等到 55s 说明它等满了两块。

**把块切到 512，理论上每块约 3.5 秒，短请求最坏等待应从 55s 降到个位数秒。**
代价是预填吞吐可能下降（分块越细，每块的并行效率越低）。

本轮启动 C 组（`PREFILL_CHUNK=512`）后会话与服务器断连，**该组未测完**。
这是下次最应该先做的一件事——它是本轮机制分析直接推出的结论，
且不依赖厂商任何修复。

## 六、待验的其它调度旋钮

| 旋钮 | 假设 |
|---|---|
| `--chunked-prefill-size 512/1024` | **首选**，见上 |
| `--schedule-policy`（现 fcfs，可选 lpm/lof/priority 等） | `lof`（最短优先类）可能让短请求插队 |
| `--schedule-conservativeness` | 影响调度器接纳新请求的激进程度 |
| `--enable-priority-scheduling` + 请求优先级 | 从业务侧显式区分交互式与批处理请求 |

## 七、给业务侧的即时建议（不依赖任何修复）

在调度层修好之前，**网关层可以直接规避**：

1. **长上下文请求与交互式请求分流到不同实例**——这是最彻底的办法，
   我方本就有多条可用线路（0728 回退线、0811 无投机线）
2. 或对长 prompt 请求限流，避免它们在交互高峰期进入

否则一个用户粘贴 8K 代码，同一实例上其他所有人的首字延迟就会从 0.6 秒变成 55 秒。
