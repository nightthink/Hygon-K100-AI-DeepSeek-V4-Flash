# 调优记录 · 轮次 34：队头阻塞 86 倍，且不是旋钮能解决的

日期：2026-08-15
承接：轮次 33（4-bit 四条路全断，内核方向确认穷尽）

## 一、为什么转向调度层

轮次 25–33 把内核与量化方向走到底，结论是**天花板由厂商构建与打包决定**。
调度层是唯一系统性没碰过的一层——它不改变单流 tok/s，
但决定**多请求同时到达时用户实际等多久**。

## 二、测法

编程助手场景的真实痛点不是单流速度，而是：
**某个请求正在预填长上下文时，其它交互式请求要等多久才吐出第一个字。**

`tests/bench_hol.py`：先发一个约 8K token 的长 prompt 占住预填，
1.5 秒后并发发 4 个短请求，用流式接口量 TTFT，
以"无干扰时的短请求 TTFT"为基准算放大倍数。

## 三、结果：86 倍，且三种配置都救不了

| 配置 | 受扰短请求 TTFT（中位） | 放大倍数 | 长请求 TTFT | 单流解码 |
|---|---|---|---|---|
| **A 基线**（chunk 4096） | 54.79 s | **86.2×** | 56.29 s | 33.2 tok/s |
| B `--enable-mixed-chunk` | 55.66 s | 87.6× | 57.16 s | 33.5 tok/s |
| C `chunked-prefill-size=512` | 52.24 s | 82.8× | 52.91 s | 33.2 tok/s |

无干扰时短请求 TTFT 均为 **0.63–0.64 s**。

**三组几乎没有差别。** 两个最像解药的旋钮都无效。

## 四、日志揭示的真正机制（推翻了我们的假设）

原假设：短请求要等长预填的**分块边界**，所以把分块切小就能插进去。
C 组把分块从 4096 切到 512（每块实测仅 1.5–2 秒）后仍然阻塞 52 秒，假设不成立。

调度器日志给出了答案：

```
01:43:59  Prefill batch, #new-seq: 1, #new-token: 512
01:44:01  Prefill batch, #new-seq: 1, #new-token: 512
01:44:02  Prefill batch, #new-seq: 1, #new-token: 512
...（连续 16+ 批，每批 #new-seq 恒为 1，中间没有任何 Decode batch）
```

**每个预填批次自始至终只有一个序列，短请求根本没有被接纳进来**——
哪怕每个分块只占 1.7 秒，调度器也不在分块之间插入新请求。

结论：**sglang 的分块预填同一时刻只允许一个请求在途，且必须跑完。**
这是框架的调度设计，不是可调参数。`--enable-mixed-chunk` 解决的是
"解码请求被预填挤掉"，而我们遇到的是"**预填请求**被预填挤掉"——两回事。

## 五、反向结论：不要把 chunk 切小

C 组下预填吞吐约 **300 tok/s**（512 tok / 约 1.7 s），
而 4096 分块时文档基线为 437 tok/s。

**切小分块既没换来 TTFT 改善，还损失了预填吞吐——`chunked-prefill-size` 应保持 4096。**
这条已回写生产启动器（未做改动，即维持原值）。

同时确认 `--enable-mixed-chunk` 对解码性能中性（33.5 vs 33.2），
误开无性能损失，但也无收益。

## 六、可行的缓解：在网关层分流

既然框架内解决不了，就在框架外解决：

**把长上下文请求与交互式请求路由到不同实例。**

我方本就有多条可用线路，天然适合这种分流：

| 线路 | 适合承接 |
|---|---|
| 0811 + DSpark（主线，33.2 tok/s） | 交互式短请求 |
| 0728 + MTP（回退线，18.7 tok/s） | 长上下文批处理 |
| 0811 无投机（52.2 tok/s 聚合，任意温度稳定） | 采样场景 / 长上下文 |

否则一个用户粘贴 8K 代码，同实例上其他所有人的首字延迟就从 0.6 秒变成 55 秒。

**这是本次全程唯一一个不依赖厂商修复、且能直接改善用户体感的改动**，
其收益（55 s → 0.6 s）远大于单流从 33 提到 50 tok/s。

## 七、尚未验证的调度旋钮

以下未测，但按第四节的机制分析，它们改变的是**请求排序**而非
"分块预填独占"这一根本约束，因此预期收益有限：

- `--schedule-policy`（现 fcfs，可选 lpm / lof / priority / dfs-weight 等）
- `--schedule-conservativeness`
- `--enable-priority-scheduling` + 请求优先级

若要在框架内根治，需要的是"允许多个请求同时处于分块预填状态"或
"长预填可被抢占"，这属于向上游提需求的范畴。

## 八、方法论备注

本轮再次印证了当日反复出现的一条：**先取证，再调旋钮。**

前两组（mixed-chunk、切小分块）都是基于对机制的**猜测**去试参数，各花约 20 分钟重启，
全部无效；而一次 `docker logs | grep 'Prefill batch'` 就直接暴露了
`#new-seq: 1` 这个决定性事实。若一开始就看日志，能省下两轮实验。
