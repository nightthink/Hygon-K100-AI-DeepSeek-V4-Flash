承接：轮次 30（应用层手段收敛到厂商侧）

轮次 30 结尾列了四项未测小项，本轮一次跑完。做法是一个后台编排脚本，

预填每次换前缀，避开前缀缓存。

### B：强开共享专家融合 → 静默输出乱码

模型 `config.json` 里 `n_shared_experts: 1`，确实有共享专家，所以日志那句
"Config does not support fused shared expert(s)" 是**代码侧的能力判定**没通过，
不是模型没有。加上 `--enforce-shared-experts-fusion` 后判定被覆盖，日志变成
`Shared experts fusion optimization enabled.`，服务正常启动、不报任何错。

然后问它 `37*89-156`：

```
 7

1、5年. 202【 1.4

【解在【实】小分【】数学【数学】 4 个【题 在
```

彻底的乱码。量化指标同步佐证：**accept rate 从 0.62 崩到 0.03**——草稿模型与目标模型
几乎完全不一致，说明目标模型的数值已经坏了；解码速度也从 32.49 掉到 7.91。

**这是本项目第二次遇到「启动正常、无报错、数值静默错误」**（第一次是轮次 25 的 bf16 KV）。
差别在于：bf16 KV 那次指标全面**变好**（更难发现），这次指标全面**变差**（较易发现）——
但如果只看预填吞吐（158.73，与基线基本持平）仍会漏掉。

> 那句"Config does not support"是**保护性判定，不是保守默认**。强开即废。

### C：换 MoE runner → 权重加载期就崩

```
File "sglang/srt/layers/moe/fused_moe_triton/layer.py", line 579, in _load_w13
    loaded_weight = loaded_weight.narrow(
IndexError: start out of range (expected to be in range of [-2048, 2048], but got 10240)
```

`triton_kernel` runner 期望的专家权重布局与 compressed-tensors w8a8 对不上
（10240 = 5 × 2048，偏移按另一种布局算）。好在它**响亮地失败**——加载阶段直接退出，
不存在带病运行的风险。

### D：开预填 cuda graph → 捕获期就崩

```
NotImplementedError: unsupported forward_mode=<ForwardMode.EXTEND: 1>
```

启动时先给了个提示 `cuda_graph_config[prefill].backend='full' is experimental.
Use breakable or tc_piecewise for production workloads.`，随后在捕获阶段崩溃。

值得一提的是**捕获范围本来是对的**：`num_tokens=[4, 8, ..., 3840, 4096]`，
上限正好等于 `chunked_prefill_size=4096`，覆盖完整分块。也就是说这条路失败的原因
不是覆盖不足，而是 DSV4 的 EXTEND 前向压根没实现图捕获。
轮次 27 见到的那条 "auto-disable rules" **同样是保护性的**。

## 二、本轮的方法论收获

三项全否，而且**三项都是框架已经自行关闭或默认避开的东西**，每一次框架的默认值都是对的：

| 项 | 框架的默认行为 | 强行覆盖的后果 |
|---|---|---|
| 共享专家融合 | 判定"config 不支持"后禁用 | 静默乱码 |
| MoE runner | `auto` | 加载期崩溃 |
| 预填 cuda graph | auto-disable 规则关闭 | 捕获期崩溃 |

结合轮次 26（MoE 配置目录为空的警告只值 +1%）与轮次 27（cuda-graph-max-bs 假设被日志证伪），
**在这个平台上，"看起来是被保守关掉的优化"通常是被正确关掉的。**
真正的问题不在这些开关里，在构建缺口（轮次 28）与内核缺陷（轮次 29）里。

## 三、附带发现：我们在用 2 倍的权重跑这个模型

查共享专家配置时顺带核对了权重规格：

| | 目录大小 | 每参数（按 284B 计） |
|---|---|---|
| 原始 `DeepSeek-V4-Flash-0731` | **156 GB** | ≈ 4.4 bit |
| 反量化 `dsv4-0731-bf16` | 567 GB | ≈ 16 bit |
| 我方 `dsv4-0731-w8a8-dspark` | **292 GB** | ≈ 8.2 bit |

`config.json` 里 `expert_dtype: fp4`，抽样 safetensors 头部显示专家张量占 **90.3%** 的字节。
原始模型的专家权重本就是 **4-bit**（fp4 双值打包进 int8 容器，配 ue8m0 块缩放）。

轮次 26 判定瓶颈是"每步从 HBM 搬多少字节专家权重"。而我们的量化管线把专家从 4-bit
升到了 8-bit —— **等于以模型原生设计约 1.9 倍的权重流量在运行**。

原因正是轮次 28 查到的：gfx928 上 `cutlass_w4a8_moe_mm` 等整个低比特算子族没有编进
ROCm 构建，想跑 4-bit 也没有内核。

这把给海光的诉求从"要是支持 4-bit 就好了"变成了**"请让我们能按模型原本的格式跑"**——
不是锦上添花，是补回被平台拿走的一半带宽预算。

### 顺带更正一处文档错误

`num_experts_per_tok` 是 **6**，不是此前文档里写的 8。所以解码每步是
6 token（DSpark 验证窗口）× 6 专家 = **36 行**摊到 256 个专家上，不是 48 行。
结论（平均每专家远不足 1 行，耗时由权重搬运主导）不变，数字已更正。
