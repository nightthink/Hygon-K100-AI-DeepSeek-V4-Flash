## 轮次24：DSpark 并发崩溃深挖 — 六种手段全试 + 关键对照实验

日期：2026-08-14 上午。目标：解决"非贪心（temperature>0）+ 高并发触发 GPU 硬件异常"。

### 一、已排除的六种缓解手段（每次实验需重启服务约 13 分钟）

| 手段 | 结果 |
|---|---|
| 缩小 draft 块 gamma 5→3（验证窗口 6→4） | ❌ 仍崩 |
| 显式 `top_k=50` 走稀疏路径（绕开稠密全词表兜底） | ⚠️ 0/8 → 4/8，仍崩 |
| `--max-running-requests 4` 限流（日志确认队列生效） | ❌ 仍崩 |
| **强制 accept 内核走 torch 参考实现**（镜像自带 torch/triton 双实现，新增补丁反转 `kernels/dispatch.py::inputs_on_cuda`） | ❌ 仍崩 |
| **JIT 版 moe_align 内核**（`SGLANG_EXPERIMENTAL_LORA_OPTI=1` + `SGLANG_OPT_USE_JIT_KERNEL_MOE_ALIGN=1`，替换预编译版） | ❌ 仍崩 |
| 降并发到 2 | ✅ 可用但无实用价值 |

**一条曾被误认的线索**：崩溃时 HSA 队列分析点名 `moe_align_block_size_kernel`，而该内核从启动起就在刷警告
`Launch params (1024,1,1) are larger than launch bounds (256)`（以 1024 线程启动却按 256 线程编译）。
但换 JIT 版后警告与崩溃均照旧，且该警告在**稳定的贪心运行**中同样存在——判定为伴随现象，非根因。
（该警告本身仍值得海光修复，已列入 Bug 报告附录建议。）

### 二、关键对照实验：0811 镜像 + 不开 DSpark

| 配置 | temp=0.7 × 8 并发 |
|---|---|
| 0728 镜像 + 4 月版（生产线） | ✅ 一直稳定（历次压测均用 0.7） |
| **0811 镜像 + 0731 + 无投机** | ✅ **8/8 成功，聚合 52.2 tok/s** |
| 0811 镜像 + 0731 + DSpark | ❌ HSA_STATUS_ERROR_EXCEPTION 0x1016 |

**结论：崩溃是 DSpark 特有的，不是 0811 镜像或 sglang 0.5.15 在 gfx928 上的通病。**
该实验一次性排除了镜像、权重、gfx928 triton 注意力后端、采样器兜底四个方向。
启动器见 `scripts/start_0811_nospec.sh`。

（注：0811 无投机的首轮测试曾出现 0/8 超时，重测即 8/8——那是首批请求撞上 triton JIT 编译，
非崩溃。测任何新路径都必须先预热再测，否则会把 JIT 耗时误判为故障。）

### 三、新发现：预热能显著改善（安全并发 2 → 4）

此前所有非贪心并发测试中，那 8 个请求都是该路径的**首批**请求，等于 8 路并发同时触发 triton JIT。
改为"先单请求预热非贪心路径，再渐进升并发"后：

| 并发（temp=0.7） | 无预热 | **先预热** |
|---|---|---|
| 2 | ✅ | ✅ |
| 4 | ❌ GPU 硬件异常 | ✅ **32.4 tok/s** |
| 8 | ❌ GPU 硬件异常 | ❌ 仍失败，但**故障形态变软**（无 HSA 异常、无 watchdog，表现为 detokenizer 停止响应） |

即：**并发 JIT 编译是崩溃的重要诱因之一，但不是全部**。预热把安全并发从 2 提到 4，
并把 8 并发的硬件异常降级为软挂起。验证脚本见 `tests/warmup_then_bench.sh`。

### 四、当前可用边界（生产决策依据）

| 场景 | 状态 |
|---|---|
| 贪心（temperature=0），1/2/4/8/10 并发 | ✅ 全稳，单流 33.8、8 并发 50.2、10 并发 46.3 |
| 非贪心 + 预热 + ≤4 并发 | ✅ 可用（4 并发 32.4 tok/s） |
| 非贪心 + ≥8 并发 | ❌ 不可用 |

> 本表**修订**了轮次 23 的结论"非贪心超过约 2 路并发即崩"——加入预热后安全并发为 4。

**补充依据**：DeepSeek 官方 API 的 thinking 模式**本就忽略 temperature**（官方文档明示）；
但 0731 模型卡对**本地部署**推荐 `temperature=1.0`（`generation_config.json` 亦为 do_sample=true/temp=1.0）。
故"锁贪心"是可行的工程折中，但确实偏离官方本地部署推荐值，需业务侧知情。

### 五、给海光的诉求（已写入 Bug 报告补充版）

DSpark 非贪心接受路径在 gfx928 上并发触发 `HSA_STATUS_ERROR_EXCEPTION 0x1016`。
已排除：draft 块大小、稀疏/稠密 topk 路径、运行批量限流、accept 内核 torch 回退、moe_align 实现。
已定位诱因之一：该路径首次并发触发 triton JIT 时更易崩（预热可把安全并发从 2 提到 4）。
上游 `v0.5.15.post1_dev` 分支 2026-08-05 后无任何 hang/并发相关 DSpark 提交。

### 六、方法论小结（写给后来者）

1. **看不到调用栈的故障，靠对照实验而不是参数扫描**。前五种手段都是"改一个可能相关的参数
   再试"，花了近一天全无收获；第六步换成"固定其它变量、只切掉 DSpark"，一次实验就把
   嫌疑范围从整个软件栈缩到一个模块。
2. **警告不等于根因**。`moe_align` 的 launch bounds 警告足够刺眼、又恰好在崩溃现场被点名，
   但它在稳定运行中同样存在。判据是"关掉它后现象是否变化"，不是"它看起来是否可疑"。
3. **测新路径必须先预热**。triton JIT 的首次编译既能把正常耗时伪装成故障（0/8 超时），
   又能把并发故障放大成硬件异常——两次误判都出在这上面。
