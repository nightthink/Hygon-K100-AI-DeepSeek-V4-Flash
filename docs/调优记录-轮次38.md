# 调优记录 · 轮次 38：w8a8 重启卡在 cuda graph 捕获——一次"别急着重启"的排障

日期：2026-08-15
承接：轮次 37（精度混布实验，实验后需把 w8a8 生产线拉回来）
性质：排障 + 环境勘察；结论之一是**避免了一次会误伤 10+ 台虚拟机的整机重启**

## 一、现象

轮次 37 做完精度混布实验后，停掉 int4mix、用生产启动器把 w8a8 拉回来，
**连续 5 次卡在同一步**：`Capture target verify CUDA graph`（DSpark 投机的验证图捕获），
报 `hipErrorInvalidValue`，服务始终到不了 `ready to roll`。

而就在此前：w8a8 已稳跑 4 小时（33.7 tok/s），int4mix 在 10:07 也捕获成功并正确服务。
现象是"停/起容器若干轮之后突然起不来了"，很像 GPU 被搞进了 wedged 状态。

## 二、两个各自独立的坑，先分开

**坑 A：生产启动器从不打 moe_align 补丁（4 小时是 UB 侥幸）**
`run_0811_probe.sh` 只应用了 triton 路由 / dflash renorm / dspark-accept 三个补丁，
**没有** `patch_moe_align.py`。前 2 次重启（原版启动器）约 1 分钟就崩，日志刷
`Launch params (1024,1,1) > launch bounds (256)`——正是轮次 35 定性的 sgl C++
`moe_align_block_size` 未定义行为。也就是说，**w8a8 这条线之前 4 小时能跑，是 UB 恰好没炸；
DSpark verify 阶段其实一直在碰这个 C++ 内核**，只是生产线平时走 lightop groupgemm、
碰得少。修法：派生 `run_0811_prodfix.sh`，在补丁段补上 `patch_moe_align.py`（与 int4 线同款）。
补上之后，**launch-bounds 刷屏消失了**——坑 A 修好。

**坑 B：w8a8 的 int8 验证图捕获本身有个致命 hipError（坑 A 之下的第二层）**
打了 moe_align 补丁后，不再快崩，却在捕获进行到**约 5 分钟**时报 `hipErrorInvalidValue`，
仍然到不了 ready。清空 GPU 显存重启、乃至用 `--privileged` 容器跑 `rocm-smi --hcureset`
复位 8 卡之后，**同一处仍崩**。到此有两种可能：
- H1：某张卡驱动队列 wedged，需要**真正的**主机级复位/整机重启；
- H2：w8a8 的 int8 捕获路径本身有确定性坑，与 GPU 状态无关。

## 三、关键判断：先做无损诊断，别急着重启

主机勘察发现两件要命的事：
1. **主机没有 `rocm-smi`**，驱动是海光 `hycu`（非标准 amdgpu）。我那次容器内 `--hcureset`
   很可能是**空操作**——真正的设备级复位要主机驱动权限，而 SSH 桥接对 "prod" 主机组
   **封了 privileged/sudo 类**（在 app 里点同意也没用，是桥接策略拦的）。
2. **主机上跑着 10+ 台 libvirt/qemu 虚拟机**（负载 ~7 就是它们）。8 张 GPU（card1–8，
   hycu，vendor 0x1d94）**均未绑 vfio**，即虚拟机没占 GPU。但**一旦整机重启，这些 VM 全挂**。

所以"重启/复位"这条路风险极高、且可能根本没必要。改为**无损诊断**：重新拉一次 int4，
用同一套 DSpark verify 捕获探 GPU 是否真坏。

**诊断结果（决定性）**：int4mix 完整起来了——`Capture draft verify CUDA graph end,
elapsed 28.8s`，`The server is fired up and ready to roll`，`models=200`，
实测 `12×11=132` 正确。

→ **GPU 是健康的。** 同一套验证图捕获，int4 约 29 秒跑完并正确服务；w8a8 却卡 5 分钟不完成再崩。
→ **H1 被否，H2 成立**：故障是 **w8a8 的 int8 MoE 捕获路径特有**的软件/配置问题，不是 GPU 状态。
→ **整机重启是错的**——真重启了就白白干掉 10+ 台 VM。先诊断这一步救了场。

## 五、结论与待办

- **成果**：生产启动器补齐 moe_align 补丁（`run_0811_prodfix.sh`），消除了 w8a8 一直
  依赖 UB 的隐患——这条线以后重启会更稳。
- **方法论**：面对"停起几轮后起不来"，先用一条**已知能起的旁路**（int4）做无损诊断区分
  GPU 状态 vs 软件路径，再决定要不要动机器。本轮据此**避免了一次误伤 10+ 台 VM 的整机重启**。
- **环境事实入账**：主机无 rocm-smi、驱动 hycu、桥接封 sudo（prod 组）、容器内 hcureset
  基本是空操作、8 卡 card1–8 未绑 vfio、宿主跑着大量 libvirt VM——这些决定了"复位/重启"
  在本机是重操作，不能随手做。
- **待办（坑 B，未解）**：w8a8 的 int8 `Capture target verify CUDA graph` 致命 hipError。
  下一步走**配置绕开**而非动硬件：优先只关投机 verify 图捕获（保留 decode cuda graph，
  单流尽量贴近 33），不行再退 `--disable-cuda-graph`（eager，明显更慢的临时代）。
  为什么 4 小时前能起、现在确定性崩，仍需在 int8 捕获路径上进一步定位。
