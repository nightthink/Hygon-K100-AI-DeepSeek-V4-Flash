# 调优记录 · 轮次 29：把 DSpark 采样崩溃锁定到「拒绝重采样分支」

日期：2026-08-14
承接：轮次 24（对照实验排除镜像/权重/注意力后端）

## 一、先澄清一个常被问到的问题：这不是模型要求

被迫锁 `temperature=0` 常被误解为"V4-Flash 或 Think 模式需要贪心"。**不是。**
模型自带的 `generation_config.json` 写得很清楚：

```json
{ "do_sample": true, "temperature": 1.0, "top_p": 1.0 }
```

DeepSeek 官方默认就是**采样**，温度 1.0。我们锁贪心是在违背模型推荐用法，纯属绕开缺陷。
Think 与贪心也没有绑定关系——`chat_template_kwargs={"thinking":true}` 在 `temperature=0`
下能正常产出 `reasoning_content`（轮次 27 验收）。

三条证据说明是实现缺陷而非模型约束：

1. **故障形态不可能来自模型**：报的是 `HSA_STATUS_ERROR_EXCEPTION 0x1016`（GPU 硬件异常）
   加 watchdog 超时。模型层面的采样问题只会产生坏文本，打不出 HSA 硬件故障。
2. **对照实验已隔离变量**：同镜像、同权重、同卡，只关掉 DSpark，temperature=0.7 × 8 并发
   → 8/8 成功（52.2 tok/s）。采样本身完全正常，翻转结果的唯一变量是 DSpark。
3. **热身能改变阈值**：预热非贪心路径后安全并发从 2 提到 4，是惰性初始化/竞态特征。
   确定性的模型约束不会对"热过身没有"有反应。

## 二、判别实验：问题在代码路径，还是在残差分布数学？

投机解码在两种模式下的验证完全不同：

- **贪心验证**：比对 argmax，token 相同即接受，几乎不需要额外内存。
- **采样验证**：必须做拒绝采样才能保持目标分布不变——按 `p_target/p_draft` 判接受，
  **拒绝时还要从残差分布 `max(0, p−q)` 归一化后重新采样**。

关键探针：**`temperature=0.7` + `top_k=1`**。它在数学上等价于贪心（候选集只有一个 token，
无论怎么缩放 logits 采出来的必然是 argmax），但**走的是完整的采样代码路径**——
`do_sample` 分支、接受判定、残差缓冲全都要过一遍。唯一不会发生的是"拒绝后重采样"。

全程不预热采样路径（预热会把安全并发从 2 抬到 4，污染结论）。

### 结果

| 配置 | 并发 | 结果 | accept rate |
|---|---|---|---|
| `temperature=0`（基线） | 8 | ✅ 8/8 | 0.60–0.77 |
| **`temperature=0.7` + `top_k=1`** | 8 | ✅ **8/8，服务健康**（48.9 tok/s 聚合） | 0.60–0.77 |
| `temperature=0.7` + `top_k=2` | 8 | ❌ **`HSA_STATUS_ERROR_EXCEPTION 0x1016`** | 0.25 |
| `temperature=0.7`（全词表） | 8 | ❌ 2/8 超时，detokenizer 卡死 | 0.26–0.27 |

**结论：采样代码路径本身没有问题，随机性本身也没有问题。
触发条件是「拒绝后重采样」这条分支被真正执行。**

`top_k=1` 时草稿 token 几乎全部被接受（accept rate 0.6+），重采样分支根本不进；
`top_k` 一旦放到 2，accept rate 立刻掉到 0.25——**七成以上的草稿 token 被拒绝**，
重采样分支被密集触发，故障随即出现。从 1 到 2 就是分界线。

## 三、这个定位解释了此前所有的观测

| 现象 | 用「重采样分支有缺陷」如何解释 |
|---|---|
| 贪心全并发安全 | 贪心验证走的是另一套路径，根本没有残差重采样 |
| `top_k=1` 安全 | 走采样路径，但接受率高，重采样分支不进 |
| 并发越高越容易崩 | 同时在飞的拒绝事件越多，该分支的并发压力越大 |
| 预热能把安全并发 2→4 | 该分支存在惰性初始化，预热填上了一部分 |
| **`SGLANG_DSPARK_FORCE_TORCH_ACCEPT=1` 无效** | **该开关覆盖的是「接受判定」内核，不是「拒绝后重采样」分支** |

最后一条此前一直是个说不通的疑点——如果故障在接受内核里，torch 回退理应绕开它。
现在它与其余现象自洽了：**回退换掉的不是出问题的那段代码。**

## 四、故障表现不唯一，但根因同一

同样是 8 并发采样，两次实验的表现并不相同：

- `top_k=2`：`HSA_STATUS_ERROR_EXCEPTION 0x1016`，队列 abort（经典签名）
- 全词表采样：进程全部存活（8 个 scheduler + detokenizer 均在 `Sl` 睡眠态），
  但 detokenizer 不再响应，健康检查报
  `Server couldn't get a response from detokenizer for last 20 seconds`

**硬件异常与死锁是同一缺陷的两种表现**，符合竞态/越界类问题的典型特征——
具体撞到什么，取决于坏访问落在哪里。报障时两种表现都应列出，避免被当成两个独立问题。

- 复现最小配置：`--speculative-algorithm DSPARK`，`temperature=0.7`，**`top_k=2`**，并发 8

修好这一条，本线就能按模型推荐的方式跑采样，而不是被锁在 `temperature=0`。
