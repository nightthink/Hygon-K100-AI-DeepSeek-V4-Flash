配套产出：`scripts/start_prod_dspark.sh`（含贪心护栏、Think 行为差异、KV dtype 禁改三条警告）。

### 2. MoE 内核调优工具链

`scripts/moe_tuning/`：调优器的 per-channel 量化崩溃补丁、裁剪后的搜索空间生成器
（1600 → 108/96 个配置，**15×**）、两轮结果合并脚本、容器化入口。

顺带发现调优器两个可报障的问题：per-channel 下 `None % 64` 直接 TypeError；
ROCm 默认搜索空间含病态组合（单配置耗时 85 秒，ETA 被拖到 16:58:08）。

### 3. 把采样崩溃定位到「拒绝重采样分支」

用 `temperature=0.7 + top_k=1`（数学等价贪心，但走完整采样代码路径）做判别：

| 配置 | 8 并发结果 | accept rate |
|---|---|---|
| `temp=0.7` + `top_k=1` | ✅ 8/8 通过 | 0.60–0.77 |
| `temp=0.7` + `top_k=2` | ❌ HSA 0x1016 | **0.25** |

**采样代码路径本身没问题，随机性本身也没问题**，触发条件是拒绝事件密集发生时
走的那条重采样分支。这个定位顺带解释了此前说不通的疑点：
`SGLANG_DSPARK_FORCE_TORCH_ACCEPT` 无效，是因为它换掉的是「接受判定」内核，
不是「拒绝后重采样」分支。

复现脚本：`tests/probe_sampling_crash.py`。

### 4. gfx928 构建目标探针

`tests/probe_arch.sh`：几十秒查出各内核库编进了哪些架构、某个算子是否真被编入。

```
sgl_kernel  → gfx906 gfx926 gfx928 gfx936 gfx938  ✅
aiter       → 仅 gfx938                            ❌
deep_ep     → 仅 gfx936 gfx938                     ❌
```

这张表顺带解开了长期疑问：启动器里那一长串 `SGLANG_*AITER*=false`
**不是调优偏好，是整个 aiter 库没有本卡的设备代码**。

### 5. 发现我们在以模型原生 1.9 倍的权重流量运行

| | 大小 | 每参数（284B 计） |
|---|---|---|
| 原始 `DeepSeek-V4-Flash-0731` | **156 GB** | ≈ 4.4 bit |
| 我方 w8a8 | **292 GB** | ≈ 8.2 bit |

模型的专家权重原生就是 4-bit（专家占 90.3% 字节）。而瓶颈恰恰是每步搬多少字节权重。

进一步查明 sglang 有 `is_fp4_experts` 自动识别与完整的后端映射，
其中 gfx928 上唯一可能可用的是 `humming`——**但 `humming` 包没随镜像发布**
（集成代码 `mxfp4_humming_moe.py` / `humming_utils.py` 都在，`import humming` 失败）。
默认 `auto` 会把 fp4 反量化成 fp8，所以"跑在 8-bit"是这条代码路径的既定行为。

## 四、数据勘误

`num_experts_per_tok` 是 **6**，不是此前文档里写的 8。

解码每步是 6 token（DSpark 验证窗口）× 6 专家 = **36 行**摊到 256 个专家上，不是 48 行。
结论（平均每专家远不足 1 行，耗时由权重搬运主导）不变，数字已在各处更正。
